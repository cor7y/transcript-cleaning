# 双源转录对齐

> 同一段录音有两份转录源时的处理方法。通用，与客户无关。
> 做完这里的对齐和发言人还原，再回到 SKILL.md 按清洗规则出稿。

典型情况：一份**分段正确但发言人标签不可靠**（麦克风共用/切换），另一份（如另一引擎的"听悟原文" docx）**发言人更可靠但分段过碎**。

## 1. 流程总览

```
问麦克风位置 → parse 检查解析 → align 出三张表 → 定标签映射（歧义问用户）
→ sample 抽样定文本基准 → 只人工看被标记的轮次 → 按 SKILL.md 规则出稿 → reverse-check
```

## 2. 先问清每份源来自哪支麦克风

两份录音是两个**麦克风位置**，不只是两个引擎。**文本质量按人好坏，不按文件好坏**：某支麦离谁近，谁的文本就干净。

开工前问用户：每份源是哪支麦/哪台设备录的？谁离哪支麦近？有没有远程参会者？有没有自己的会议笔记？

- 共用会议室设备时，平台会把屋里所有未匹配声纹的人**一律并进设备主人的标签**；另一引擎的匿名 `发言人N` 编号对这些人反而更有区分度。**不要因为一个标签有名字就相信它胜过匿名编号。**
- 远程参会者是例外：各自设备进来的音频最干净（没经过"扬声器放出来再被麦收进去"），平台给的账号标签也最权威。
- 认不出的匿名编号，拿用户自己的会议笔记交叉验证——笔记通常按发言人分节，内容能和某个编号逐句对上；剩下的用麦克风位置名单排除法兜底。

## 3. 程序对齐，不要手读

**不要在主上下文里逐轮手工比对**，几十上百轮就把上下文烧光了。用 `scripts/align_sources.py`：

原理：两份都抽成 `(speaker, text)` 列表 → 各拼成一条去标点字符流 → `difflib.SequenceMatcher` 跑全文 → 每个 matching block 映射回"基准稿第几轮 / 参考稿第几轮" → 按字符数给每一轮加权投票。得到**每轮一个置信度**，只有票数混杂的需要人工看。实测约 85% 的轮次能自动定下来。

```bash
S=<skill目录>/scripts/align_sources.py
python3 $S parse A.md                     # 先确认解析对了：轮数、发言人分布是否合理
python3 $S parse B.docx
python3 $S align A.md B.docx --out align_out   # 三张表 + 逐轮投票，明细写到 align_out/turns.tsv
python3 $S sample A.md B.docx --speaker 冯     # 并排看某人的长句，定文本基准
python3 $S reverse-check A.md A_cleaned.md     # 收尾：抓漏段
```

- 支持 `.docx` / `.md` / `.txt` / `.json`（`[{"speaker","text"}]`）。`parse` 结果不对（轮数离谱、正文被当成标签）时，传 `--speaker-regex '^(?P<spk>\S+)\s+\d{2}:\d{2}$'` 这类整行正则，或自己先转成 JSON。
- 基准稿（第一个参数）= 分段正确的那份；参考稿 = 另一份。
- 10 万字级别约 1 分钟。在有短时限的 shell 里用 `nohup python3 ... > align.log 2>&1 &` 后台跑再读 log。
- `turns.tsv` **不要整表读进上下文**，只筛"标记"列为 `票数混杂 / 标签不一致 / 未覆盖` 的行：`awk -F'\t' '$7=="票数混杂"||$7=="标签不一致"||$7=="未覆盖"' align_out/turns.tsv`

### 三张必跑的表（`align` 一次全出）

1. **标签交叉表**（先看）：「基准稿发言人 × 参考稿发言人」按匹配字符数交叉统计，一眼看出映射关系和异常。
   实例：跑出 `刘松杨→刘 96%`、`陆虎→发言人c10 96%`、`吴昊→吴 94%`，而基准稿中段才出现的 `发言人 3→冯 92%`——一行就定死了"发言人 3 是冯喆君声纹丢失后的第二标签"。
   同时看**匹配区间**（首尾 matching block 的位置），就知道第二份源覆盖了基准稿的哪个区间。
   脚本会对两种碰撞打 ⚠：多个参考标签落在同一基准标签上（设备主人合并 或 第二声纹桶），多个基准标签落在同一参考标签上（换麦后的第二标签）。
2. **分桶覆盖率表**：基准稿每 25 轮一桶，打印每桶匹配字符占比。
   实例：前 16 桶都在 68~95%、**第 400 轮起整齐掉到 0%**——第二份源根本没录到后 1/3，不是对齐失败。**分不清"没对上"和"没录到"会让人白白去调对齐参数。** 脚本会把这类区段标成 `参考稿未录到`，不计入人工量。
3. **反向覆盖检查**（收尾必做，见第 7 节）。

`align` 还会顺带输出：零重叠标签对、相邻近重复段、对方未覆盖的长片段——都是第 5 节那些坑的线索。

## 4. 选文本基准：抽样验证，不要凭假设

正确做法：挑更全更干净的那份当**文本基准**，用另一份的轮次边界去**切分和重标**，再逐轮把麦更近的那份的措辞替换回来。**不要选定一个文件就从头用到尾。**

**但"麦更近"是假设，不是结论——对齐后必须抽样验证再定基准。**
实例：用户说 part2 是"在某人旁边新开的麦克风，可能对他的发言录音质量更好"，实际比对下来 part2 **整体更差**（同一句里把"日产"听成"资产"，内容也更短更碎）。最后主稿全程当文本基准，part2 只用来做发言人还原和交叉验证。

判断方法：`sample --speaker X` 挑十来处该发言人的长句左右并排，看哪份的**专有名词和数字**更对。

## 5. 纯投票会漏掉的坑（必须人工覆盖）

| 形态 | 判据 | 处理 |
|---|---|---|
| **一个人两个标签**（声纹中途丢失：换麦、演示者走到同事电脑前共享屏幕） | 两个标签**零重叠**（真有第五个人时两个标签会交替出现） | 当别名合并 |
| **参考稿凭空多出一个"人"** | 某标签 85% 落在基准稿另一个人身上，且与那人的标签**全程交替出现**（不是零重叠），逐条读内容全是同一身份 | 是同一支会议室麦上那人的**第二个声纹桶**，并回去 |
| **电话/免提接入的人被剁碎** | 某人刚被点名打电话之后，出现一段谁的标签都接不上的连续内容（基准稿里拆成多个碎片轮流挂在几个人名下） | 是电话那头的人。值得另起一个标签并在头部说明，**但先问用户** |
| **远端发言人的短应答**（"能听见""可以可以"）挂到了主讲人身上 | 对话上下文 | 按上下文改，哪怕算法置信度很高 |
| **多麦串音的相邻近重复** | 同一句以"残缺版+完整版"两轮出现且归给不同人；相邻轮 `SequenceMatcher` 比值 > 0.3~0.4 | 去重，保留完整版 |
| **一段里塞了问和答** | 某轮票数 40/60 分裂，且文本确实是两句（从"你/您"称呼切到"我/我们"自述） | 拆成两轮 |

注意"零重叠＝同人换标签"和"交替出现＋内容同一身份＝第二声纹桶"是**两种不同形态**，别混。

**不要假设错标只集中在一个明显区块，全文跑一遍。** 曾有一大段"受访者自述"其实是访谈者在讲自己团队的策略，位置在文件很后面，只因为对齐是全文均匀跑的才被抓到。

孤立标签（ASR 切分 artifact vs 真实但发言少的人）的判据见 SKILL.md "发言人"一节，处理前问用户。

## 6. 会议尾声的"外来会议声"

用户说"某某分钟后有外部声音被录进来"时，**先用程序找证据再动手删**：

1. 看 `align` 输出的"对方未覆盖的长片段"——两份源里**互不覆盖的长片段**往往就是只有一支麦收到的外来声音
2. 看话题是否在那附近突变

把候选边界给用户，**不要自己猜切点**。实例：用户给的答案是"只删外人进屋的会议声，保留寒暄和私聊"，跟"整段砍掉"是两种完全不同的处理。

## 7. 出稿与收尾

- 按 SKILL.md 的清洗规则出稿；发言人归属用对齐结果＋第 5 节人工覆盖后的版本。
- 头部加一行 `> 发言人：…`，交代标签映射、合并的别名、拆出的人、删掉的段。
- **反向覆盖检查（必做）**：`reverse-check 基准稿 成稿`，列出"原文 ≥8 字但成稿覆盖 <50%"的轮次，逐条确认是有意删除还是写稿漏掉。这一步能抓到整轮漏掉的段落，比人工通读可靠。

## 8. 结论性单句必须回听录音

**任何会改变产品/商务结论的单句——尤其含否定词、含"要不要系统 / 要不要我方 / 认不认"这类判断的句子——在被写进结论前必须回听录音。**

Why：清洗稿从 ASR 原文派生，两者一致**不构成独立证明**，只证明清洗没引入新错。ASR 原文本身可能漏字或多字，一个"不"字就能让结论 180° 反转。两份转录源都这么写也一样——它们可能在同一处都听错。

实例：ASR 与清洗稿均作「只要领导认为可以了，**那就不发到系统里面**」，据此推出"他认为根本不需要系统"——足以动摇整个功能存废的判断。用户回听后确认真实原话是「**那就发到系统里面**」，含义完全相反：他在**主动描述他想要的系统职责**。

How：把这类句子单独挑出来列给用户，注明"此结论挂在单句上，建议回听"；**永远不要用"原文和清洗稿一致"或"两份源一致"作为可信度理由**。
